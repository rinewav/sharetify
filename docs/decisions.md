# 設計上の決定と、その理由

2026-07-27 の設計セッションで確定した内容。**「なぜそうしたか」を残すのが目的**なので、方針を変えるときはここの前提が崩れていないかを先に確認すること。

---

## 1. 配布形態: 公開サービスとして運営する

中央サーバーは誰でも登録できる公開サービスにする。ただし成立するのは、後述の分散アーキテクチャによって中央が著作物に一切触れないから。

**検討して却下した案:**

- **中央サーバーが解決・中継をする案** — 1 つの IP から大量に取得することになり、供給元の bot 検知で技術的に停止する。同種の公開インスタンスはこれでほぼ全滅している。訴訟以前に動かない
- **完全なセルフホスト配布のみ** — 目的（友だちとの共有・同時リスニング）は達成できるが、分散構成でそれらを両立できると分かったため不要になった

## 2. 参考にした先行例と、そこから学んだこと

**iOS の類似アプリについて調べた結論: 参考にならない。**

- 同種のアプリは公式のプレーヤーを埋め込む方式で成立している。だから**ダウンロードもオフライン再生も原理的にできず、音声データにも触れない**
- つまりダウンロード機能・音声処理機能を持たせたい時点で、その方式は選べない
- そのうち最大手は 10 年運営された後、2024 年 9 月に配信停止。訴訟したが 2026 年 3 月に敗訴している
- **生き残っている側の共通点は「供給元の名前をどこにも出していないこと」**。この点は運用方針として採用した

## 3. iOS では埋め込みプレーヤーが使えない

当初「スマートフォン側は安全側に倒して埋め込みプレーヤーにする」案を検討したが、**成立しない**。

- 埋め込み方式が成立している既存アプリはネイティブアプリであり、バックグラウンド再生の権限を持てる。**PWA にその権限はない**
- cross-origin の iframe には MediaSession API が効かないため、ロック画面に曲名も操作ボタンも出せない
- **PWA でバックグラウンド再生を成立させる唯一の道は、`<audio>` 要素に実メディア URL を渡すこと**

結果として、iOS でこそ直接取得が必要という逆説的な結論になった。

## 4. NAT 越え: 用途で経路を分ける

| 用途 | 経路 | 理由 |
|---|---|---|
| 自分のスマートフォン → 自分の PC | Tailscale | 同一 tailnet なので NAT 越えが不要。正規の HTTPS 証明書も取れる |
| 同時リスニング | 中央の WebSocket | そもそも P2P 接続が要らない設計にした（次項） |

**P2P (WebRTC) は最終的に不要になった。** 検討段階では必要だったが、同時リスニングを「配信」ではなく「同期」として設計し直したことで、接続そのものが消えた。

参考までに、当初 P2P を前提にしていたときの調査結果:
- 住宅網での直接接続の成功率は約 90%、**15〜20% は中継サーバーを必要とする**
- 携帯キャリア網の多くは対称 NAT 相当で、**最も使う場面（外出先 → 自宅）が最も繋がりにくい**
- 日本の固定回線も IPv4 over IPv6 方式が普及しており、使えるポートが限られる

## 5. 中継サーバー (TURN) は立てない

同時リスニングを同期方式にしたことで不要になった。

法的には、暗号化されたまま中継するだけなら米国 DMCA 512(a) の免責要件を満たす形にできる（開始が利用者側、内容を選別しない、必要以上に保持しない）。ただし免責を主張するには問い合わせ窓口の設置と繰り返し侵害への対応方針の明示が必要になる。**そもそも不要にできたので、この論点ごと回避した。**

## 6. 自宅で運用しつつ、グローバル IP は隠す

- **中央 API と WebSocket は Cloudflare Tunnel 経由**。やり取りするのは小さい JSON だけなので、大容量配信を禁じる利用規約の条項には触れない
- VPN 上でサーバーを立てる案は不可。契約中の事業者はポート開放機能を 2023 年 7 月に廃止しており、受信接続を一切開けない
- **隠すべきは自宅のグローバル IP**（露出すると通知が回線事業者に届き、回線契約そのものが危うくなる）。**運営者の連絡先はむしろ公開する**（免責の要件であり、窓口がないと通知が届かず、いきなりドメインやホスティングを止められる）

## 7. PC がオフラインの間はダウンロード済みのみ再生

受け入れる。代わりに**ダウンロード機能を必須要素に格上げ**した。

この決定により「ストリーミング」と「ダウンロード」が同じコードパスになり、実装が単純化する副次的な利点がある。

## 8. 音声の運び方

**曲全体を取得してから再生する方式**を採る（逐次デコードではなく）。

- iOS で確実に動く
- ダウンロード・キャッシュとコードを共通化できる
- シークが即座に効く
- 頭出しに数秒かかるが、次の曲を先読みすれば実質ゼロにできる

長尺素材を扱いたくなったら逐次方式へ移行できる。ただし iOS の逐次再生には固有の制約があるため、その時点で実機検証が必要。

## 9. V1 のスコープ

**入れる**: 検索 / 再生 / ライブラリ / プレイリスト / ダウンロード・オフライン / last.fm 連携 / フレンド・グループ / プレイリスト共有 / **同時リスニング**

**入れない**: プレイリスト変換、ボーカル抽出

変換機能を外した理由: 主要サービスの API は新規申請が事実上止まっていたり、年額の開発者登録が必要だったり、そもそも公開 API が存在しなかったりする。単独で調査が必要な規模なので V1 には載せない。

## 10. 検証フェーズは独立させず、実装順序で吸収する

未検証の前提が 4 つある（解決処理の安定性 / 大きなデータの転送 / iOS でのバックグラウンド再生 / キャッシュの保持挙動）。

独立した検証フェーズは設けないが、**V1 で最初に書くコードを再生経路にする**。UI やログインから作ると、後半で再生が成立しないと判明したときに作り直しになる。

---

## 最大のリスクは法的なものではない

**供給元の技術的対策によって、ある日突然すべての利用者が再生できなくなること。** 発生確率は法的措置より桁違いに高い。

対策は設計に組み込み済み:
- 失敗は必ず理由付きで返す
- ダウンロード済みのみ再生する縮退動作へ落とす
- 解決コンポーネントを更新できる経路を用意する
